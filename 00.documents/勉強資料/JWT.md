## 【JWT（JSON Web Token）ベース認証方式の説明】（JP）

### 1. 🔍 JWTとは何か？

JWT は、クライアントとサーバー間の通信において **ユーザー情報（Claims）** を安全に送信するために定義されたオープン標準（RFC 7519）です。

単なるランダムな文字列であるセッションIDとは異なり、JWT 自体にユーザー認証に必要な情報が含まれており、**デジタル署名（Signature）** が付与されているため、改ざんの有無をサーバー側で即座に検証できます。

---

<br>

### 2. JWTの3つの構成要素

JWT はドット（.）区切りで、次の3つの部分から構成されます。

<center>
<i>Header.Payload.Signature</i>
</center>

<br>

| 部分 | 内容 | 役割 |
| :--- | :--- | :-- |
| **Header（ヘッダー）** | トークンの種類と暗号化方式を定義 | トークンタイプ（JWT）、署名アルゴリズム（HS256、RS256 など） |
| **Payload（ペイロード）** | クライアントに渡す実データ（Claims） | userId、role などの認証情報、トークンの有効期限（exp） |
| **Signature（署名）** | トークンの改ざん防止 | Header と Payload をサーバーの **秘密鍵（Secret Key）** でハッシュ化して生成 |

> ⚠️ 注意：Payload は Base64 でエンコードされているだけで、暗号化されているわけではありません。そのため、パスワードなどの機密情報を Payload に含めてはいけません。

---

<br>

### 3. JWTベース認証の流れ（Flow）

JWT 認証は主に次の5ステップで構成されます。

| ステップ | 主体 | 動作 | 説明 |
| :--- | :--- | :-- | :-- |
| **1. ログイン要求** | クライアント → サーバー | `userAccount` と `password` を送信 | クライアントがサーバーにログイン情報を送信します。 |
| **2. トークン生成** | サーバー | DB検証後、JWTを生成 | サーバーはDBでユーザー認証に成功すると、`userId` などを含む Payload を作成し、**Secret Key** で署名して JWT を発行します。 |
| **3. トークン送信** | サーバー → クライアント | JWT を返却 | 生成された JWT を HTTP レスポンスヘッダー（例：`Authorization: Bearer <token>`）や Cookie に含めてクライアントへ返します。 |
| **4. 認可リクエスト** | クライアント → サーバー | JWT を付与して API リクエスト | クライアントは保護されたリソース（例：`/auth/me`、`/workspace/create`）にアクセスするたびに JWT をリクエストヘッダーに付与します。 |
| **5. トークン検証** | サーバー | 署名の有効性を検証 | サーバーは受信した JWT の署名を Secret Key で検証します。署名が有効であれば Payload をデコードし、`userId` を取得して、そのユーザー権限で処理を行います。 |

---

<br>

### 4. JWT認証方式のメリット

| メリット | 説明 |
| :-- | :-- |
| Stateless（ステートレス） | サーバーがクライアントの状態（セッション）を保持する必要がありません。トークン自体にすべての情報が含まれるため、サーバー負荷が軽減され、スケールアウトが容易になります。 |
| 拡張性（Scalability） | 複数サーバー構成（マイクロサービスなど）において、中央集権的な認証サーバー（セッションサーバー）が不要です。同一の Secret Key を共有していれば、どのサーバーでもトークン検証が可能です。 |
| モバイルフレンドリー | トークンはモバイル環境や異なるドメイン間の API 通信（CORS）において、Cookie ベースのセッション方式よりも柔軟に利用できます。 |

## [JWT (JSON Web Token) 기반 인증 방식 설명] (KR)


### 1. 🔍 JWT란 무엇인가?

JWT는 클라이언트와 서버 간의 통신 시 **사용자 정보(Claims)** 를 안전하게 전송하기 위해 정의된 개방형 표준(RFC 7519)입니다.

단순한 무작위 문자열인 세션 ID와 달리, JWT 자체는 사용자 인증에 필요한 정보를 담고 있으며, **디지털 서명(Signature)** 이 되어 있어 위변조 여부를 서버에서 즉시 확인할 수 있습니다.

---

<br>

### 2. JWT의 3가지 구성 요소 

JWT는 점(.)을 기준으로 세 부분으로 나뉩니다.
<center>
<i>Header.Payload.Signature</i>
</center>
<br>

| 부분 | 내용 | 역할 |
| :--- | :--- | :-- |
| **Header (헤더)** | 토큰의 타입과 암호화 방식 명시 | 토큰 타입(JWT), 서명 알고리즘(HS256, RS256 등) |
| **Payload (페이로드)** | 실제 클라이언트에게 전달할 정보(Claims) | userId, role 등 인증에 필요한 정보, 토큰 만료 시간(exp) |
| **Signature (서명)** | 토큰의 위변조 방지 | Header와 Payload를 서버의 **비밀 키 (Secret Key)** 로 해시하여 생성 |

> ⚠️ 주의: Payload는 인코딩(Base64)되어 있을 뿐, 암호화된 것이 아닙니다. 따라서 비밀번호와 같은 민감 정보는 절대 Payload에 넣으면 안 됩니다.

---

<br>

### 3. JWT 기반 인증 과정 (Flow)

JWT 인증은 크게 4단계로 이루어집니다.

| 단계 | 주체 | 동작 | 설명 |
| :--- | :--- | :-- | :-- |
| **1.로그인 요청** | 클라이언트 → 서버 | `userAccount`와 `password` 전송 | 클라이언트가 서버에 로그인 정보를 보냅니다. |
| **2. 토큰 생성** | 서버 | DB 검증 후 JWT 생성 | 서버는 DB에서 사용자 인증에 성공하면, `userId` 등의 정보를 포함한 Payload를 만들고, **Secret Key** 로 서명하여 JWT를 발급합니다. |
| **3. 토큰 전달** | 서버 → 클라이언트 | JWT 전송 | 생성된 JWT를 HTTP 응답의 헤더(예: `Authorization`: `Bearer <token>`)나 쿠키에 담아 클라이언트에 전달합니다. |
| **4. 인가 요청** | 클라이언트 → 서버 | JWT를 첨부하여 API 요청 | 클라이언트는 보호된 리소스(예: `/auth/me`, `/workspace/create`)에 접근할 때마다 이 JWT를 요청 헤더에 담아 보냅니다. |
| **5. 토큰 검증** | 서버 | 서명 유효성 검사 | 서버는 요청받은 JWT의 서명을 자체 Secret Key로 검증합니다. 서명이 유효하면 Payload를 디코딩하여 `userId` 정보를 얻고, 해당 사용자의 권한으로 작업을 처리합니다. |

---

<br>

### 4. WT 인증 방식의 장점

| 장점 | 설명 |
| :-- | :-- |
| Stateless (무상태성) | 서버가 클라이언트의 상태(세션)를 저장할 필요가 없습니다. 토큰 자체에 모든 정보가 있으므로, 서버 부하가 줄고 서버 확장(Scale-out)이 용이합니다. |
| 확장성 (Scalability) | 여러 서버로 구성된 환경(마이크로 서비스 등)에서 별도의 중앙 집중식 인증 서버(세션 서버) 없이도 모든 서버가 같은 Secret Key만 알고 있다면 토큰 검증이 가능합니다. |
| 모바일 친화적 | 토큰은 모바일 환경이나 다른 도메인 간의 API 통신(CORS)에서 쿠키 기반의 세션보다 훨씬 유연하게 사용될 수 있습니다. |
